---
name: Almoxarifado name-based merge must exclude equipment-linked items
description: Merging "duplicate name" almoxarifado_itens rows without checking equipamento_vinculado_tipo/_id destroys legitimate one-row-per-physical-unit equipment records.
---

Rule: any script that groups/merges `almoxarifado_itens` rows by identical `nome` must EXCLUDE rows where `equipamento_vinculado_tipo IS NOT NULL` (i.e. `equipamento_vinculado_id` set). These rows are not duplicate imports — they are one-row-per-physical-equipment-unit records (locado/próprio scaffolding/formwork: diagonais, sapatas, painéis, pranchões), each linked 1:1 to a row in `equipamentos_locados`/`equipamentos_proprios`. This is the same class of "legitimate individual tracking" exception as items with a reference code embedded in the name.

**Why:** A prior merge grouped purely by normalized name + `tipo_controle='estoque'`, which does not distinguish this case. ~806 equipment-linked rows got merged/deleted. The existing idempotent startup job `backfillAlmoxFromEquipamentos` (`server/lib/almoxEquipamentoSync.ts`) detected the resulting orphans (no almox item linked to an active equipamento) and auto-recreated all 806 rows on next restart — fully restoring functional linkage/quantity (source-of-truth `equipamentos_*` tables were never touched) — but this raw INSERT path never generated `codigo_interno`, so 806 items came back with NULL codes. Also, per-item movement/transfer/loan HISTORY tied to the original deleted rows was unrecoverable (it had been repointed to the wrong "canonical" survivor row during the merge, and temp backups were already cleared by the time this was discovered).

**How to apply:** Before grouping almoxarifado items for any merge/dedup by name, always add `AND equipamento_vinculado_tipo IS NULL` to the candidate query. Also note: `almoxEquipamentoSync.ts`'s three raw-SQL INSERT paths (`ensureAlmoxItemForEquipamento` + both queries in `backfillAlmoxFromEquipamentos`) were patched to always generate a `MAT-NNNN` code via `pg_advisory_xact_lock`, so this specific NULL-code gap is now closed — but the general "check equipment link before merging by name" rule still applies to any future dedup work.
